## 매 실행의 규칙

1. 먼저 사용량 도구로 계정의 현재 한도를 확인한다. `rateLimitsByLimitId`가 있으면 그것을 우선하고 사용 중인 모델에 적용되는 모든 창을 살핀다. 5시간 등 단기 창이 85% 이상이거나 주간 창이 90% 이상이면 새 구현을 시작하지 않는다. 사용량 조회 불가·한도 도달·지출 제한도 작업 확대 없이 체크포인트 후 종료한다. 다음 정기 실행에서 다시 확인한다. 사용량이 회복될 때까지 장시간 sleep, 바쁜 재시도, 즉시 반복 실행을 하지 않는다. 리셋 크레딧 사용·추가 구매·모델 변경은 자동으로 하지 않는다.
2. 여유가 있으면 이 파일의 재개 지점, 기준 문서의 해당 절, 적용되는 저장소 지침과 필요한 코드만 읽는다. 전체 조사를 매번 반복하지 않는다. 한 실행에 **미완료 항목 하나 또는 그 안의 작은 검증 가능한 단위 하나**만 진행하고 종료한다. 큰 항목은 먼저 아래 표에 세부 단위를 적어 여러 실행으로 나눈다.
3. 시작 전에 상태를 `진행 중`으로 기록하고, 범위·예정 수정 파일·완료 조건을 적는다. 약 25분의 작업 시점 또는 큰 변경 직후에 사용량을 다시 확인해 정리 시간을 남긴다. 실제 안전한 중단점까지 유연하게 정리하되, 여유가 줄면 새 하위 작업을 시작하지 않는다. 모델이 중단되더라도 작업 파일과 이 기록에서 복구할 수 있어야 한다.
4. 사용자 변경을 보존한다. `git status`, 현재 브랜치, remote URL을 먼저 확인하고, 기록되지 않은 수정은 임의로 스테이징·삭제·덮어쓰기하지 않는다. 다른 작업과 충돌하면 분리된 작업 공간에서 진행할 수 있는지 판단하고, 해결할 수 없는 충돌만 기록한다. 중복 실행·이미 진행 중인 동일 작업을 시작하지 않는다.
5. 푸시 전 `git fetch origin`으로 원격 상태를 확인한다. 작업 브랜치 원격 갱신이 있으면 이력을 보존하여 통합하고 관련 검증을 다시 한다. 강제 푸시, 원격 브랜치 삭제, 사용자 작업 초기화는 하지 않는다. `upstream`에는 푸시하지 않는다. `main` 병합·서비스 배포는 별도 요청이 없는 한 하지 않는다.
6. 동작 변경에는 의미 있는 회귀 검증을 포함한다. 저장소 표준은 `npm test`, `npm run typecheck`, `npm run build`이다. 빌드와 타입 검사는 생성 파일 경합을 피하도록 순차 실행한다. 문서만 바꾼 실행에는 `git diff --check`와 문서 검토면 충분하다. UI 변경은 해당 UI 스킬을 적용하고 가능한 로컬 브라우저에서 휴대폰/데스크톱 크기·키보드·레이아웃을 확인한다. 실제 모바일 마이크, 유료 API, 사람 평가를 수행하지 못했으면 그 한계를 그대로 남긴다.
7. 성공한 단위를 관련 파일과 이 진행 기록만 명시적으로 스테이징하여 커밋한다. `git push -u origin codex/feedback-learning-loop`로 푸시하고 원격 브랜치 SHA가 로컬 HEAD와 같은지 확인한다. 미완성·검증 실패 코드는 완료로 표시하거나 정상 변경으로 푸시하지 않는다. 중단된 변경은 로컬 파일과 아래 재개 메모로 보존한다. 푸시 실패 시 검증된 로컬 커밋을 보존하고 다음 실행에서 먼저 푸시를 재시도한다.
8. 종료 전 재개 지점·완료/진행 상태·검증·수정 파일·다음 행동·미푸시 여부를 갱신한다. 커밋 자체의 SHA는 그 커밋 안에 넣으려 하지 말고 다음 실행에서 기록하거나 `git log`로 확인한다. 기다리는 상태가 똑같으면 불필요한 문서 커밋과 알림을 만들지 않는다.
9. 사용자에게는 항목 완료와 푸시, 새로운 실패, 필요한 실제 기기/사용자 확인, 전체 완료 같은 의미 있는 변화만 알린다. 동일한 사용량 대기는 조용히 끝낸다.
10. 모든 구현과 검증·푸시가 끝나면 최종 결과를 기록하고 이 heartbeat를 도구로 일시정지한다. 사람 평가나 실제 기기가 없어서 독립 작업이 더 이상 불가능한 경우에도 그 항목을 `외부 검증 대기`로 남기고 한 번 알린 뒤 일시정지한다. 대기를 전체 완료로 바꾸지 않는다. 재개 요청을 받으면 같은 자동화를 갱신한다.

위 사용량 임계값과 실행 길이는 이 작업의 보수적인 운영 기준이다. 토큰을 정확히 강제 제한하는 장치는 아니며, 계정 한도나 앱 실행 상태로 정기 실행이 지연될 수 있다. 로컬 파일을 쓰는 자동 실행에는 컴퓨터와 Codex 앱이 실행 중이어야 한다.

## 구현 체크리스트

**범위: 연습 후 결과(채점) 화면.** 검토 문서의 `우선 1` 중에서도 결과 화면과 그 화면을 채우는 피드백 생성까지만 이번 범위로 둔다. 대상 파일은 `src/components/ExamResult.tsx`, `src/components/FeedbackDetails.tsx`, `src/app/api/feedback/route.ts`, `src/lib/feedback.ts`, `src/lib/types.ts`와 관련 `tests/`이다.

**설계 결정 변경 — 두괄식은 유지한다.** 검토 문서의 `유지·축소·삭제·추가 결정` 표는 두괄식→디테일→감정 공통 판정을 `삭제·교체`로 적었으나, OPIc 대비가 목표이므로 **유지·조정**으로 바꾼다. 서술형 문항에서 핵심을 먼저 말했는지는 그대로 판정한다. 없애는 것은 (1) 근거와 무관하게 매 답변에 3단계를 모두 `좋음/보강`으로 표시하는 것과 (2) `문법은 항상 마지막` 같은 고정 우선순위뿐이다. 근거가 부족한 단계는 `판단 보류`로 표시한다. 참고로 현재 코드는 이미 `requiresFrontLoadedOpening()`으로 유형별 두괄식 기준을 나누고 있으므로, 이 판정 로직 자체는 지우지 않고 확장한다.

`대기 → 진행 중 → 완료`로 바꾼다. 수행하지 못한 현실 검증은 `외부 검증 대기`로 구분한다. 한 실행에 하위 단위 하나만 진행한다.

- 관찰: `FeedbackDetails.tsx`의 `FlowStep`이 `structure.topic/detail/feeling`을 항상 `good` 여부로만 그린다. `판단 보류`를 넣으려면 화면과 스키마를 함께 넓혀야 하므로 R-01a에서 타입만 먼저 넓히고 화면은 R-03c에서 바꾼다.
- 관찰: `requiresFrontLoadedOpening()`은 `FREE_OPENING_TYPES` 집합 하나로 판단한다. R-02b는 이 집합에서 `roleplay_experience`만 빼는 것으로 끝나지 않고, `route.ts`의 `structureRules`와 화면 라벨(`두괄식 도입` / `요청·문제 전달`)까지 함께 본다.
- 레거시 읽기·신규 쓰기·렌더링은 중간 커밋에서도 호환되어야 한다. 저장된 피드백을 새 기준으로 조용히 변환하지 않는다.
- 외부 의존 검증은 독립 구현을 막지 않게 별도로 기록하고, 가능하지 않은 실제 기기·사람 검증을 완료로 체크하지 않는다.
